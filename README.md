# DailyOps (MVP)

Simple full-stack MVP: React (Vite + TS + Tailwind + shadcn/ui) frontend and NestJS + Prisma + PostgreSQL backend with JWT auth. Login, Dashboard, Customers, Products, Leads (Sales Pipeline, with Excel import), Quotations, Sales Orders, Proforma Invoices, Job Execution Orders (production), Materials (Material Master, manufacturing catalog), Suppliers (Supplier Master, with Excel import/export), and Enterprise RBAC (Departments, Roles, Permissions, Users, permission-driven menus and API guards) are functional, per scope.

```
dailyops/
  frontend/   React + Vite + TS + Tailwind + shadcn/ui
  backend/    NestJS + Prisma + PostgreSQL + JWT + Swagger
  docker-compose.yml   (PostgreSQL only)
```

## 1. Start PostgreSQL (Docker)

```bash
cd dailyops
docker compose up -d
```

This starts Postgres on `localhost:5432` with db `dailyops`, user `dailyops`, password `dailyops`.

## 2. Backend setup (runs locally, not in Docker)

```bash
cd dailyops/backend
cp .env.example .env
npm install
npx prisma migrate dev
npm run seed
npm run dev
```

`npx prisma migrate dev` applies every migration under `prisma/migrations` (including `add_customer`, `add_product`, `add_lead_management`, `add_lead_conversion`, `add_quotation_management`, `add_sales_order_management`, `add_proforma_invoice_management`, `add_job_execution_order_management`, `add_material_master`, `add_lead_industry`, `add_supplier_master`, `add_enterprise_rbac`, and `add_username_and_force_password_change`) and regenerates the Prisma client. If you already ran earlier migrations on this database, running it again just applies whichever ones are new — no data loss. There is no seed data for products, leads, quotations, sales orders, proforma invoices, job execution orders, materials, or suppliers; all are created entirely through the UI (Material Categories and Units, and Suppliers, can also be bulk-loaded via Excel import). Departments, Permissions, Roles, and exactly one default User **are** seeded — see below.

`npm run seed` seeds Enterprise RBAC data: 7 Departments, the full Permission catalog, and 6 Roles with their permissions assigned (Administrator, Sales Manager, Sales Executive, Production, Finance, Stores) — but **only one User**, the built-in System Administrator bootstrap account (see below). Every other user must be created dynamically from **Administration → Users** by an Administrator; nothing else is hardcoded. Re-running the seed is safe — it upserts everything and re-syncs the Administrator role's permission set, rather than duplicating rows.

Installing dependencies for this module also pulls in `xlsx` (Excel read/write) and `multer` + `@types/multer` (file upload handling for the import endpoint) — both added to `backend/package.json`.

Backend runs at `http://localhost:4000`.
Swagger docs: `http://localhost:4000/api/docs`

Seeded default user — the only hardcoded account in this system:
- Name: **System Administrator**
- Username: `admin`
- Email: `admin@smartrotamac.com`
- Password: `Admin@123`
- Role: **Administrator** (every permission)
- Status: Active
- **Force password change on first login is enabled** — the very first login with this account is immediately redirected to a Change Password screen and cannot reach anything else in the app until a new password is set. See Business Rules (Enterprise RBAC) below.

### Endpoints

Auth:
- `POST /auth/login` — body `{ identifier, password }`, where `identifier` is either the user's **username** (e.g. `admin`) or their **email** (e.g. `admin@smartrotamac.com`) — both work interchangeably in the same field. Returns `{ accessToken, user }`, where `user` includes `mustChangePassword`.
- `GET /auth/profile` — requires `Authorization: Bearer <token>`, returns current user (same shape as login's `user`, recomputed fresh)
- `POST /auth/change-password` — requires `Authorization: Bearer <token>` only (no permission check — every authenticated user can always change their own password); body `{ currentPassword, newPassword }`. This is the only way `mustChangePassword` is ever cleared. `401 Unauthorized` if `currentPassword` doesn't match.

Customers (all require `Authorization: Bearer <token>`):
- `GET /api/v1/customers?page=1&limit=20&search=acme` — paginated list (20/page), active customers only, `search` matches company name, contact person, or phone
- `GET /api/v1/customers/:id` — single customer
- `POST /api/v1/customers` — create; body `{ companyName, contactPerson, phone, email?, gstNumber? }`
- `PATCH /api/v1/customers/:id` — partial update, same fields as create
- `DELETE /api/v1/customers/:id` — soft delete (sets `isActive=false`); customer disappears from the default list but the row remains in the database

Products (all require `Authorization: Bearer <token>`):
- `GET /api/v1/products?page=1&limit=20&search=fan&category=HVLS+Fans` — paginated list (20/page), active products only; `search` matches name, category, or SKU; `category` is an optional exact-match filter
- `GET /api/v1/products/categories` — distinct list of categories currently in use (feeds the category filter/suggestions in the UI)
- `GET /api/v1/products/:id` — single product
- `POST /api/v1/products` — create; body `{ name, category, sku?, description?, price? }`
- `PATCH /api/v1/products/:id` — partial update, same fields as create
- `DELETE /api/v1/products/:id` — soft delete (sets `isActive=false`)

Dashboard (requires `Authorization: Bearer <token>`):
- `GET /api/v1/dashboard/stats` — returns `{ customers, products, leads, quotations, salesOrders, proformaInvoices, jeoPending, materialsCount, lowStockCount, outOfStockCount, suppliers }`. `customers` and `products` are live `count()` queries against active rows; `leads`, `quotations`, `salesOrders`, and `suppliers` are live `count()` queries against rows where `deletedAt` is null (matching each module's soft-delete convention); `proformaInvoices` counts rows where `status` is not `CANCELLED` (this model has no `deletedAt`/`isActive` column — see Business Rules below); `jeoPending` counts Job Execution Orders where `status` is exactly `PENDING` (per scope: "JEO Pending Count", not "not completed"); `materialsCount` counts active Materials; `outOfStockCount` counts active Materials where `currentStock <= 0`; `lowStockCount` counts active Materials where `0 < currentStock <= reorderLevel` (a two-column comparison Prisma can't express in a `where` filter, so it's computed in-memory over the small set of non-zero-stock materials — see Business Rules (Materials) below).

Leads (all require `Authorization: Bearer <token>`):
- `GET /api/v1/leads?page=1&limit=20&search=acme&status=NEW&priority=HIGH&source=WEBSITE&assignedTo=Priya&dateFrom=2026-01-01&dateTo=2026-12-31&sortBy=createdAt&sortOrder=desc` — paginated list (20/page), excludes soft-deleted leads; `search` matches lead number, company name, contact person, email, phone, or title; `sortBy` is whitelisted to createdAt/updatedAt/companyName/estimatedValue/nextFollowUp/expectedCloseDate/leadNumber/priority/status
- `GET /api/v1/leads/:id` — single lead with its linked products (and each product's details)
- `POST /api/v1/leads` — create; auto-generates `leadNumber` (e.g. `LD-000001`); body `{ companyName, contactPerson, phone, title, designation?, email?, alternatePhone?, city?, state?, country?, industry?, description?, products?: [{ productId, quantity, unitPrice?, remarks? }], estimatedValue?, priority?, source?, expectedCloseDate?, nextFollowUp?, remarks?, assignedTo? }`
- `PATCH /api/v1/leads/:id` — partial update, same fields as create; if `products` is included it fully replaces the lead's product list
- `PATCH /api/v1/leads/:id/status` — dedicated status-change endpoint; body `{ status }`. Setting status to `WON` does **not** create a Customer — see Business Rules below
- `DELETE /api/v1/leads/:id` — soft delete (sets `deletedAt`); lead disappears from the default list but the row remains in the database
- `POST /api/v1/leads/:id/convert` — converts a `WON` lead into a `Customer`; see Business Rules below for the guard conditions and what gets created/updated
- `GET /api/v1/leads/import/template` — streams a blank `.xlsx` with the exact header row the import expects: Company Name, Contact Person, Email, Phone, City, State, Industry, Lead Source, Status, Remarks. Registered ahead of `GET /:id` for the same reason Materials' `export` route is — though here there's actually no collision risk either way, since `import/template` is two path segments and `:id` is one.
- `POST /api/v1/leads/import/preview` — multipart file upload (field name `file`, `.xlsx`/`.xls`/`.csv`; only a Company Name column is required, every other column — and the file can be missing any/all of them — is optional), parses and validates every row **without inserting anything**. Returns `{ totalRows, validCount, invalidCount, duplicateCount, rows: [{ row, companyName, contactPerson, email, phone, city?, state?, industry?, source, status, remarks?, result: "valid"|"invalid"|"duplicate", errors?, duplicateReason? }] }`. This is the "Preview Data" step — see Business Rules (Lead Import) below for exactly what's validated and how duplicates are detected.
- `POST /api/v1/leads/import` — body `{ rows: [...] }` (the same row shape the Preview response returns — typically just its `valid` rows, though the client can send anything and every row is re-validated from scratch here regardless). Bulk-inserts everything that classifies as valid and not a duplicate, skips the rest, and returns the same shape as Preview but with `result: "created"` in place of `"valid"` for the rows actually inserted (plus a `createdCount` instead of `validCount`, and `leadNumber` on each created row).

Quotations (all require `Authorization: Bearer <token>`):
- `GET /api/v1/quotations?page=1&limit=20&search=acme&status=DRAFT&customerId=<uuid>&dateFrom=2026-01-01&dateTo=2026-12-31&sortBy=createdAt&sortOrder=desc` — paginated list (20/page), excludes soft-deleted quotations; `search` matches quotation number or the linked customer's company name/contact person; `sortBy` is whitelisted to createdAt/updatedAt/quotationNumber/grandTotal/validUntil/status
- `GET /api/v1/quotations/:id` — single quotation with its customer and line items (each with product details)
- `POST /api/v1/quotations` — create; auto-generates `quotationNumber` (e.g. `QT-2026-000001`, year-scoped sequence); body `{ customerId, items: [{ productId, description?, quantity, unitPrice? }], gstPercent?, validUntil?, notes?, terms? }`. `unitPrice` defaults to the product's catalog price if omitted. The backend always (re)computes each item's `lineTotal`, the quotation `subtotal`, `gstAmount`, and `grandTotal` server-side — client-submitted totals are never trusted.
- `PATCH /api/v1/quotations/:id` — partial update, same fields as create; if `items` is included it fully replaces the quotation's item list and recomputes totals; changing `gstPercent` alone (without `items`) also recomputes GST/grand total against the existing subtotal
- `PATCH /api/v1/quotations/:id/status` — dedicated status-change endpoint; body `{ status }` (`DRAFT` | `SENT` | `ACCEPTED` | `REJECTED` | `EXPIRED`)
- `DELETE /api/v1/quotations/:id` — soft delete (sets `deletedAt`); quotation disappears from the default list but the row remains in the database

Sales Orders (all require `Authorization: Bearer <token>`):
- `GET /api/v1/sales-orders?page=1&limit=20&search=acme&status=DRAFT&customerId=<uuid>&quotationId=<uuid>&dateFrom=2026-01-01&dateTo=2026-12-31&sortBy=createdAt&sortOrder=desc` — paginated list (20/page), excludes soft-deleted sales orders; `search` matches sales order number, quotation number, or the linked customer's company name/contact person; `sortBy` is whitelisted to createdAt/updatedAt/salesOrderNumber/grandTotal/orderDate/deliveryDate/status
- `GET /api/v1/sales-orders/:id` — single sales order with its customer, a summary of its originating quotation (id/number/status), and line items (each with product details)
- `POST /api/v1/sales-orders` — create; auto-generates `salesOrderNumber` (e.g. `SO-2026-000001`, year-scoped sequence, same pattern as `Quotation.quotationNumber`); body `{ quotationId, items: [{ productId, quantity, unitPrice?, discount?, description? }], orderDate?, deliveryDate?, paymentTerms?, advancePercentage?, gstPercent?, discount?, billingAddress?, shippingAddress?, specialInstructions?, remarks? }`. `customerId` is **not** part of the request body — it is always taken from the linked quotation. Every submitted item's `productId` must already exist on the quotation (400 otherwise); `unitPrice`/`description` default to what the quotation recorded if omitted. Fails with 400 if the quotation isn't `ACCEPTED`, and 409 if a sales order already exists for that quotation.
- `PATCH /api/v1/sales-orders/:id` — partial update of everything except `quotationId` (immutable once created); same item rules as create if `items` is included
- `PATCH /api/v1/sales-orders/:id/status` — dedicated status-change endpoint; body `{ status }` (`DRAFT` | `CONFIRMED` | `PRODUCTION_STARTED` | `READY_FOR_DISPATCH` | `DISPATCHED` | `COMPLETED` | `CANCELLED`)
- `DELETE /api/v1/sales-orders/:id` — soft delete (sets `deletedAt`); sales order disappears from the default list but the row remains in the database

Proforma Invoices (all require `Authorization: Bearer <token>`):
- `GET /api/v1/proforma-invoices?page=1&limit=20&search=acme&status=DRAFT&customerId=<uuid>&salesOrderId=<uuid>&dateFrom=2026-01-01&dateTo=2026-12-31&sortBy=createdAt&sortOrder=desc` — paginated list (20/page); `search` matches invoice number, the linked sales order number, or the linked customer's company name/contact person; `sortBy` is whitelisted to createdAt/updatedAt/invoiceNumber/grandTotal/invoiceDate/validUntil/status
- `GET /api/v1/proforma-invoices/:id` — single invoice with its customer and its linked sales order (including that sales order's line items and products)
- `POST /api/v1/proforma-invoices` — create; auto-generates `invoiceNumber` (e.g. `PI-2026-000001`, year-scoped sequence, same pattern as `salesOrderNumber`/`quotationNumber`); body `{ salesOrderId, invoiceDate?, validUntil?, paymentTerms?, bankName?, accountNumber?, ifscCode?, branch?, notes? }`. **No `customerId` and no items/amounts are accepted** — `customerId`, `subtotal`, `discount`, `tax`, and `grandTotal` are always copied server-side from the referenced Sales Order. Fails with `404` if the sales order doesn't exist, and `409` if a non-cancelled Proforma Invoice already exists for that sales order.
- `PATCH /api/v1/proforma-invoices/:id/status` — dedicated status-change endpoint; body `{ status }` (`DRAFT` | `SENT` | `EXPIRED` | `CANCELLED`)
- There is no `PATCH /api/v1/proforma-invoices/:id` (general edit), no `DELETE`, and no PDF endpoint yet — all deliberate, per scope (see Business Rules below).

Job Execution Orders (all require `Authorization: Bearer <token>`):
- `GET /api/v1/job-execution-orders?page=1&limit=20&search=acme&status=PENDING&priority=HIGH&customerId=<uuid>&salesOrderId=<uuid>&dateFrom=2026-01-01&dateTo=2026-12-31&sortBy=createdAt&sortOrder=desc` — paginated list (20/page); `search` matches JEO number, the linked sales order number, or the linked customer's company name/contact person; `sortBy` is whitelisted to createdAt/updatedAt/jeoNumber/deliveryDate/priority/status
- `GET /api/v1/job-execution-orders/:id` — single JEO with its customer, quotation reference (id/number/status), linked sales order (including that sales order's line items and products), and its Production Checklist
- `POST /api/v1/job-execution-orders` — create; auto-generates `jeoNumber` (e.g. `JEO-2026-000001`, year-scoped sequence, same pattern as `invoiceNumber`/`salesOrderNumber`); body `{ salesOrderId, priority?, assignedTo?, remarks? }`. **No `customerId`, `quotationId`, `deliveryDate`, or products are accepted** — `customerId`, `quotationId`, and `deliveryDate` are always copied server-side from the referenced Sales Order, and a `ProductionChecklist` row (all steps unchecked) is created alongside it in the same request. Fails with `404` if the sales order doesn't exist, and `409` if an active (not yet `COMPLETED`) JEO already exists for that sales order.
- `PATCH /api/v1/job-execution-orders/:id/status` — dedicated status-change endpoint; body `{ status }` (`PENDING` | `MATERIAL_READY` | `ASSEMBLY_STARTED` | `QC` | `READY_FOR_DISPATCH` | `COMPLETED`). Setting status to `COMPLETED` also stamps `completedAt` on the linked Production Checklist.
- `PATCH /api/v1/job-execution-orders/:id/checklist` — partial update of one or more Production Checklist booleans (`materialIssued`, `assemblyStarted`, `controllerInstalled`, `wiringCompleted`, `qcPassed`, `packed`, `readyForDispatch`); the UI's checklist checkboxes and its three quick-action buttons all call this.
- `GET /api/v1/job-execution-orders/production-dashboard` — returns `{ counts, jeos }` for the Production Dashboard page. `counts` is a count of **every** JEO (including Completed ones) broken down by all six statuses; `jeos` is the list of **active** (not yet `COMPLETED`) JEOs only, each with customer, sales order (with line items/products), and Production Checklist included, ordered by `deliveryDate` ascending. Declared before `GET /:id` in the controller so it isn't swallowed by the dynamic `:id` route.
- `GET /api/v1/job-execution-orders/:id/timeline` — returns `{ steps: [{ key, label, done, at }] }`, a best-effort cross-module lifecycle trail for one JEO (Lead Created → Customer Created → Quotation Created → Sales Order Created → Proforma Invoice Generated → JEO Generated → Production Started → QC → Dispatch → Completed). See Business Rules below for exactly what "best-effort" means here.
- There is no `PATCH /api/v1/job-execution-orders/:id` (general edit), no `DELETE`, and no Material Planning/BOM/Dispatch/PDF endpoint yet — all deliberate, per scope (see Business Rules below).

Material Categories (all require `Authorization: Bearer <token>`):
- `GET /api/v1/material-categories` — full list, sorted alphabetically. No pagination — this is a small lookup table, not a catalog.
- `POST /api/v1/material-categories` — create; body `{ name, description? }`. Returns `409 Conflict` if the name already exists (case-sensitive exact match).
- No `PATCH`/`DELETE` — categories exist only to populate the Material Form's Category dropdown and satisfy the "Required Category" foreign key; per scope there's no dedicated management UI for them.

Material Units (all require `Authorization: Bearer <token>`):
- `GET /api/v1/material-units` — full list, sorted alphabetically.
- `POST /api/v1/material-units` — create; body `{ name, symbol? }`. Returns `409 Conflict` if the name already exists.
- No `PATCH`/`DELETE`, same reasoning as Material Categories.

Materials (all require `Authorization: Bearer <token>`):
- `GET /api/v1/materials?page=1&limit=20&search=steel&categoryId=<uuid>&unitId=<uuid>&stockStatus=low_stock` — paginated list (20/page), active materials only, each with its `category`/`unit` included; `search` matches material code, name, or description; `stockStatus` is an optional filter, either `low_stock` (`0 < currentStock <= reorderLevel`) or `out_of_stock` (`currentStock <= 0`)
- `GET /api/v1/materials/:id` — single material, with `category`/`unit` included
- `POST /api/v1/materials` — create; body `{ materialCode, name, categoryId, unitId, description?, supplierId?, cost?, minimumStock?, maximumStock?, reorderLevel?, currentStock?, warehouseId?, isActive? }`. Returns `409 Conflict` if `materialCode` already exists, `400 Bad Request` if `categoryId`/`unitId` doesn't resolve to a real row.
- `PATCH /api/v1/materials/:id` — partial update, same fields as create and same validation
- `DELETE /api/v1/materials/:id` — soft delete (sets `isActive=false`), same convention as Customer/Product
- `GET /api/v1/materials/export` — streams an `.xlsx` file of every active material (columns: materialCode, name, description, category, unit, supplierId, cost, minimumStock, maximumStock, reorderLevel, currentStock, warehouseId, isActive). Registered ahead of `GET /:id` in the controller so `export` is never treated as a material id.
- `POST /api/v1/materials/import` — multipart file upload (field name `file`) of an `.xlsx`/`.xls` file with the same columns as the export. Category and Unit are resolved by name (case-insensitive), not id — spreadsheet users work with names, not UUIDs. Existing materials are matched and updated by `materialCode`; unmatched codes are created. Returns `{ totalRows, created, updated, failed, results: [{ row, materialCode, status, error? }] }` — a per-row result so partial failures (unknown category name, negative stock, missing code) don't abort the whole file; only the failing rows are skipped.

Suppliers (all require `Authorization: Bearer <token>`):
- `GET /api/v1/suppliers?page=1&limit=20&search=tata&status=ACTIVE&country=India&sortBy=createdAt&sortOrder=desc` — paginated list (20/page), excludes soft-deleted suppliers; `search` matches supplier code, supplier name, contact person, phone, email, or GST number; `country` is an optional exact-match filter (case-insensitive); `sortBy` is whitelisted to createdAt/updatedAt/supplierCode/supplierName/leadTime/status
- `GET /api/v1/suppliers/:id` — single supplier
- `POST /api/v1/suppliers` — create; auto-generates `supplierCode` (e.g. `SUP-000001`, same retry-on-conflict pattern as `Lead.leadNumber`); body `{ supplierName, gstNumber?, panNumber?, contactPerson?, phone?, email?, website?, address?, city?, state?, country?, pinCode?, paymentTerms?, leadTime?, currency?, remarks?, status? }`. **Only `supplierName` is required** — every other field is optional, per scope.
- `PATCH /api/v1/suppliers/:id` — partial update, same fields as create (never accepts `supplierCode`, which cannot be changed after creation)
- `DELETE /api/v1/suppliers/:id` — soft delete (sets `deletedAt`); supplier disappears from the default list but the row remains in the database
- `GET /api/v1/suppliers/export` — streams an `.xlsx` file of every non-deleted supplier (all fields, plus Supplier Code). Registered ahead of `GET /:id` so `export` is never treated as a supplier id.
- `GET /api/v1/suppliers/import/template` — streams a blank `.xlsx` with the exact header row the import expects: Supplier Name, GST Number, PAN Number, Contact Person, Phone, Email, Website, Address, City, State, Country, PIN Code, Payment Terms, Lead Time, Currency, Remarks, Status.
- `POST /api/v1/suppliers/import/preview` — multipart file upload (field name `file`, `.xlsx`/`.xls`/`.csv`; only a Supplier Name column is required), parses and validates every row **without inserting anything**. Returns the same `{ totalRows, validCount, invalidCount, duplicateCount, rows: [...] }` shape as Lead Import Preview, with Supplier-specific row fields. See Business Rules (Suppliers) below for exactly what's validated and how duplicates are detected.
- `POST /api/v1/suppliers/import` — body `{ rows: [...] }` (the same row shape the Preview response returns). Bulk-inserts everything that classifies as valid and not a duplicate, skips the rest, and returns the same shape as Preview but with `result: "created"` in place of `"valid"` for the rows actually inserted, plus `supplierCode` on each created row.

Enterprise RBAC — Departments, Roles, Permissions, Users (all require `Authorization: Bearer <token>` **and** the specific permission named below; see Business Rules (Enterprise RBAC) for how that's enforced):
- `GET /api/v1/departments` — full list, sorted alphabetically, each with a `_count.users`. Requires `Department.View`.
- `POST /api/v1/departments` — create; body `{ name, description? }`. Requires `Department.Create`. `409 Conflict` if the name already exists.
- `PATCH /api/v1/departments/:id` — partial update. Requires `Department.Edit`.
- `DELETE /api/v1/departments/:id` — hard delete; any User referencing this department simply has `departmentId` set to `null` (`onDelete: SetNull`). Requires `Department.Delete`.
- `GET /api/v1/permissions` — the full Permission catalog (`{ id, module, action, code, description }[]`), sorted by module then action. Requires `Permission.View`. Read-only — permissions are seeded, not managed via any create/edit/delete endpoint.
- `GET /api/v1/roles` — full list, each with its assigned `permissions` (nested `permission` details) and a `_count.users`. Requires `Role.View`.
- `GET /api/v1/roles/:id` — single role, same shape. Requires `Role.View`.
- `POST /api/v1/roles` — create; body `{ name, description?, permissionIds?: string[] }`. Requires `Role.Create`. `409 Conflict` if the name already exists.
- `PATCH /api/v1/roles/:id` — partial update; **this is also how Permissions get assigned to a Role** — sending `permissionIds` replaces that role's entire permission set (delete-all-then-recreate, same "replace the full list" convention as editing a Lead's products or a Quotation's items). Requires `Role.Edit`.
- `DELETE /api/v1/roles/:id` — deletes the role; cascades to its `RolePermission` rows and to any `UserRole` rows for users who held it (those users simply lose that role). Requires `Role.Delete`.
- `GET /api/v1/users?page=1&limit=20&search=jane` — paginated list (20/page), each with its `department` and `roles` (nested `role` details) included; `search` matches name, username, or email. Requires `User.View`.
- `GET /api/v1/users/:id` — single user, same shape. Requires `User.View`.
- `POST /api/v1/users` — create; body `{ name, username, email, password, departmentId?, roleIds?: string[] }`. `username` must be 3-32 characters (letters, numbers, dot, underscore) and unique, same as `email`. Requires `User.Create`. `409 Conflict` if the email or username already exists. Every user created this way starts with `mustChangePassword = true` — the `password` given here is a temporary one the new user must change on their first login (same as the seeded System Administrator).
- `PATCH /api/v1/users/:id` — partial update; **this is also how Role Assignment and Department Assignment work** — `roleIds` (if present) replaces the user's entire role set the same way `permissionIds` does for a Role; `departmentId` reassigns their department; `isActive: false` disables them (same soft-delete convention as Customer/Product/Material), `isActive: true` re-enables. **Does not accept `password`** — that's `POST /api/v1/users/:id/reset-password` below, a deliberately separate action. Requires `User.Edit`.
- `DELETE /api/v1/users/:id` — soft delete (sets `isActive = false`, i.e. disables the account); a disabled user's JWT is rejected on their very next request (`JwtStrategy.validate()` checks `isActive`), so they're logged out effectively immediately, not just unable to log back in. Requires `User.Delete`.
- `POST /api/v1/users/:id/reset-password` — Administrator action ("Reset Passwords"); body `{ newPassword }`. Sets a new password on someone else's account without needing to know their old one, and always sets `mustChangePassword = true` on that account, forcing them to change it again on their next login. Requires `User.Edit`.

## 3. Frontend setup (runs locally, not in Docker)

```bash
cd dailyops/frontend
cp .env.example .env
npm install
npm run dev
```

Frontend runs at `http://localhost:5173`.

## Business Rules (Leads)

- A Lead is **not** automatically a Customer. Setting a lead's status to `WON` via `PATCH /api/v1/leads/:id/status` only updates the `status` column — it does not create or touch any `Customer` record.
- Lead → Customer conversion only happens when a user explicitly calls `POST /api/v1/leads/:id/convert`, and only once the lead's `status` is already `WON`. Calling it on a lead that isn't `WON` returns `400 Bad Request`.
- Conversion creates a new `Customer` from the lead's `companyName`, `contactPerson`, `phone`, and `email`, then sets `isConverted = true`, `convertedAt = <now>`, and `customerId = <new Customer id>` on the Lead, inside a single database transaction.
- Conversion cannot be repeated: calling it again on an already-converted lead returns `409 Conflict`.
- In the Lead Details page, a "Convert to Customer" button appears only when `status === "WON"` and `isConverted === false`. After conversion, the page shows a "✓ Converted" indicator with the Customer name and a "View Customer" button that opens the Customers page.
- The Dashboard's Customers count is a live `count()` of active customers, so it automatically reflects newly converted customers on the next stats fetch — no dashboard code changed for this feature.
- A Lead can reference multiple Products via the `LeadProduct` join table (quantity, unit price, remarks per line).
- Kanban was explicitly out of scope for this delivery, but Excel import is now built (see Business Rules (Lead Import) below). The data model (status enum, `LeadProduct`, clean DTOs) is shaped so Kanban can still be added later without a schema rework — it would just be a different view over the existing `status` field and `GET /api/v1/leads`.

## Business Rules (Lead Import)

- The import template's columns (Company Name, Contact Person, Email, Phone, City, State, Industry, Lead Source, Status, Remarks) don't map 1:1 onto the existing Lead model: there's no `Title` column, but `Lead.title` is required, and there's no `industry` column on the model at all. `Title` is defaulted server-side to `"Imported Lead - <Company Name>"` (editable afterwards like any other lead); `industry` is a new additive nullable column added to the `Lead` model specifically for this feature (migration `add_lead_industry`) rather than silently dropping that column's data — it's also now a field on the manual Create/Edit Lead form and Lead Details page, not just an import-only column.
- Validation, per row: **Company Name is the only mandatory field.** Contact Person, Email, and Phone are all optional — a blank cell is accepted and that field is simply left blank (an empty string) on the created lead, not an error, and a file containing only a Company Name column is perfectly valid. If Email or Phone *is* provided, it's still format-checked (a valid email address; 10-15 digits after stripping formatting characters like spaces, dashes, `+91`, parentheses) — presence is optional, but garbage data in a filled cell is still flagged. Lead Source and Status work the same way they always have: a blank cell defaults to `OTHER`/`NEW` (the same defaults the manual Create Lead form uses); a non-blank cell that doesn't match a known value (matched case-insensitively, spaces/hyphens treated as underscores, e.g. "trade show" -> `TRADE_SHOW`) is flagged invalid rather than silently defaulted. A row with any validation failure is marked `invalid` ("Failed" in the import summary) with the specific reason(s) and is never inserted. Note that `Lead.contactPerson`/`Lead.phone` are non-nullable columns on the model — importing a row with those blank stores an empty string, not `null`, so no schema change was needed for this.
- Duplicate prevention is unchanged: Company Name + Email together (both matched case-insensitively), scoped to non-soft-deleted leads. Since Email is now optional, a row with a blank Email has nothing to match against and can never be flagged as a duplicate by this rule — it will always import (assuming Company Name is present). For rows that do have an email, this check also catches duplicates **within the same uploaded file**: rows are processed one at a time in order, and each row's duplicate check queries the database fresh — so if row 3 and row 9 of the same file share a Company Name + Email, row 9 sees row 3 already sitting in the database (inserted moments earlier in the same request) and is correctly flagged as a duplicate, with no separate in-memory tracking needed.
- The Preview step (`POST /api/v1/leads/import/preview`) runs every row through this exact same validation and duplicate-detection logic but never inserts anything — it's a dry run purely for the user to review before committing. The commit step (`POST /api/v1/leads/import`) re-runs the identical logic on whatever rows it's sent (normally just the ones Preview classified as `valid`) rather than trusting the client's earlier classification, since data could have changed in between (e.g. someone else just created a lead with the same Company Name + Email). This is deliberately the same defensive pattern Material Import uses.
- Extra columns in the uploaded file are ignored, and any of the other 9 columns can be missing from the file entirely — columns are matched by header name (case-insensitive), not position, so a file with only a Company Name column, or a reordered template, both import correctly.
- The final import summary reports three counts: **Imported** (rows actually inserted), **Duplicates** (skipped — matched an existing lead or an earlier row in the same file), and **Failed** (skipped — missing Company Name, or a provided Email/Phone/Lead Source/Status that didn't pass format/enum validation), plus the full per-row detail behind each count.
- The Dashboard's Leads count is a live `count()` of non-soft-deleted leads (unchanged from before this feature), so newly imported leads are reflected the moment the Dashboard is next viewed/refocused — no Dashboard code needed to change for this feature.
- Not changed by this update, but worth flagging: `LeadsService.convertToCustomer()` copies `contactPerson`/`phone` straight from the Lead onto the new Customer, and `Customer.contactPerson`/`Customer.phone` are themselves non-nullable. Converting an imported lead that has either field blank will create a Customer with an empty Contact Person/Phone rather than fail — no guard was added against this, since it's outside this update's scope; fill in those fields via Edit Lead before converting if that matters for a given lead.

## Business Rules (Quotations)

- Every quotation belongs to exactly one `Customer` (`customerId` is a required, enforced foreign key) and has one or more `QuotationItem` rows, each tied to a `Product` (also an enforced foreign key).
- `quotationNumber` is auto-generated in the format `SR|SPYRO|QTN|<sequence>|<year>` (e.g. `SR|SPYRO|QTN|1|2026`) — a single running sequence across all years, not one that resets each January. Quotations created before this format change keep their old `QT-<year>-<6-digit-sequence>` numbers forever; nothing renumbers them. Generated with a retry-on-conflict loop, the same pattern used for `Lead.leadNumber`.
- The Quotation PDF (Get PDF / Send Quotation) is a branded 4-page "Techno-Commercial Offer" template with a per-product Annexure-I technical specification table (from `Product.technicalSpec`) — see `QUOTATION_PDF_TEMPLATE_CHECKLIST.md` for the full write-up.
- Every new quotation starts life with `status = DRAFT`. Status only moves to `SENT` / `ACCEPTED` / `REJECTED` / `EXPIRED` via the dedicated `PATCH /api/v1/quotations/:id/status` endpoint (or the "Change Status" dialog in the UI) — never as a side effect of editing the quotation.
- `subtotal`, `gstAmount`, and `grandTotal` are always computed and stored server-side from the submitted items and `gstPercent` (default 18%); the frontend's live totals are a preview only and are never sent to or trusted by the backend.
- If an item's `unitPrice` is omitted, it defaults to that product's current catalog price (`Product.price`) at the time the quotation is created or the items are replaced.
- Deleting a quotation is a soft delete (`deletedAt` timestamp), same convention as `Lead` — the record stays in the database and just drops out of the default list.

## Business Rules (Sales Orders)

- Approving a Quotation (`PATCH /api/v1/quotations/:id/status` with `status: "ACCEPTED"`) automatically creates its Sales Order and the API response includes it (`{ ...quotation, salesOrder }`) so the UI can redirect straight to the Sales Order's detail page — see `WORKFLOW_AUTOMATION_CHECKLIST.md` for the full write-up. This only fires on the transition **into** `ACCEPTED`; the manual "Create Sales Order" button on Quotation Details still exists as a fallback for any quotation that was already `ACCEPTED` before this automation shipped.
- A Sales Order can **only** be created from a Quotation whose status is `ACCEPTED` (`POST /api/v1/sales-orders` returns `400` otherwise), and only once per quotation — attempting to create a second one for the same quotation returns `409 Conflict`. `SalesOrder.quotationId` is a unique foreign key enforcing this at the database level too. The automatic creation path above reuses this exact same guard internally, and is additionally idempotent (returns the existing Sales Order instead of erroring if one already exists).
- Customer information always auto-populates from the linked quotation's customer — `customerId` is not accepted in the request body at all, so it can never drift from the quotation's customer.
- Every item must already exist on the linked quotation (matched by `productId`); submitting a product that isn't on the quotation returns `400`. Unit price and description default to what the quotation recorded, not the live product catalog price, so the order reflects what was actually quoted. Quantity (and, if needed, a per-line discount) is what a user is expected to edit before saving.
- `salesOrderNumber` is auto-generated in the format `SO-<year>-<6-digit-sequence>` (e.g. `SO-2026-000001`), year-scoped with a retry-on-conflict loop — the same pattern as `Quotation.quotationNumber` and `Lead.leadNumber`.
- `subtotal`, `discount`, `tax`, and `grandTotal` are always computed and stored server-side: each item's tax is `(quantity × unitPrice − itemDiscount) × gstPercent / 100`; the order's `discount` is the sum of every item's discount plus an optional additional flat order-level discount; `grandTotal = subtotal − discount + tax`. The frontend's live totals are a preview only.
- `createdBy` is captured automatically from the authenticated user's JWT payload (their name) — it is never accepted from the request body.
- Every new sales order starts as `DRAFT`. Status only moves through `CONFIRMED` → `PRODUCTION_STARTED` → `READY_FOR_DISPATCH` → `DISPATCHED` → `COMPLETED` (or `CANCELLED` at any point) via the dedicated `PATCH /api/v1/sales-orders/:id/status` endpoint or the "Change Status" dialog — never as a side effect of editing the order.
- Deleting a sales order is a soft delete (`deletedAt` timestamp), same convention as `Lead`/`Quotation`.

### Future Ready: Material Planning, BOM, Production Tracking, Dispatch

The Sales Order is designed as the central business document everything downstream hangs off of. Proforma Invoice and JEO (Job Execution Order) generation are both built (see below). What's left — Material Planning / BOM, Production Tracking, and Dispatch — is designed to attach to the `JobExecutionOrder` model via new tables referencing a `jobExecutionOrderId` (the same additive-FK pattern used throughout this schema), documented as a comment above the `JobExecutionOrder` model in `schema.prisma`. No columns were added in anticipation of these, so today's schema doesn't need to change when they're eventually built.

## Business Rules (Proforma Invoices)

- A Proforma Invoice can **only** be generated from an existing Sales Order (`POST /api/v1/proforma-invoices` returns `404` if `salesOrderId` doesn't resolve to a real sales order). There is no path to create one by typing customer or product details directly — the request body doesn't even accept `customerId` or line items.
- Customer and amounts are copied from the Sales Order at generation time: `customerId`, `subtotal`, `discount`, `tax`, and `grandTotal` are all snapshotted onto the new `ProformaInvoice` row and never re-derived. `paymentTerms` also defaults from the sales order but can be overridden in the generate dialog.
- Products are **not** duplicated into a separate items table — there is no `ProformaInvoiceItem` model, per the given field list. The Proforma Invoice Details page instead reads and displays the linked Sales Order's items live via the `salesOrder` relation. This means if a sales order's items were ever edited after invoice generation, the invoice's displayed products would reflect that change, while its `subtotal`/`discount`/`tax`/`grandTotal` would not (those are frozen). This tradeoff is called out directly in the UI and in a doc comment above the `ProformaInvoice` model.
- Duplicate prevention: only one non-cancelled Proforma Invoice may exist per Sales Order at a time. Attempting to generate a second one while an active (non-`CANCELLED`) invoice exists returns `409 Conflict`. This is enforced at the application/service layer (a `findFirst` check before create), not as a database-level unique index, so it doesn't introduce any schema-drift risk against the hand-authored migrations in this project.
- `invoiceNumber` is auto-generated in the format `PI-<year>-<6-digit-sequence>` (e.g. `PI-2026-000001`), year-scoped with a retry-on-conflict loop — the same pattern as `SalesOrder.salesOrderNumber`, `Quotation.quotationNumber`, and `Lead.leadNumber`.
- Every new Proforma Invoice starts as `DRAFT`. Status only moves through `SENT` / `EXPIRED` / `CANCELLED` via the dedicated `PATCH /api/v1/proforma-invoices/:id/status` endpoint or the "Change Status" dialog. Cancelling is also what unlocks generating a fresh invoice for the same Sales Order.
- There is no edit and no delete for this module (no `deletedAt`/`isActive` column exists on `ProformaInvoice`, per the given field list) — the correction path for a wrong invoice is to cancel it and generate a new one.
- **Updated (Sales Automation):** PDF generation now exists, but only internally — `create()` renders a PDF via `PdfService` purely to attach to the automatic "PROFORMA_INVOICE" email sent to the customer (CC finance, see the Sales Automation section below). There is still no standalone download endpoint or "Download PDF" network call in the UI (that button's inline notice is unchanged) — nothing in scope called for a separate download button on this module the way Quotation's `GET :id/pdf` exists.

## Business Rules (Job Execution Orders)

- A JEO can **only** be created from an existing Sales Order (`POST /api/v1/job-execution-orders` returns `404` if `salesOrderId` doesn't resolve to a real sales order). There is no path to create one by typing customer, quotation, or product details directly — the request body doesn't accept any of them.
- Customer, Quotation reference, Sales Order reference, and Delivery Date are all copied from the Sales Order at generation time (`customerId`, `quotationId`, `deliveryDate` are snapshotted columns on `JobExecutionOrder`, never re-derived). Products are **not** duplicated into a separate items table — there is no `JobExecutionOrderItem` model, per the given field list — so, like Proforma Invoice, the JEO Details page reads and displays the linked Sales Order's items live via the `salesOrder` relation.
- Duplicate prevention: only one active (not yet `COMPLETED`) JEO may exist per Sales Order at a time. JEO has no `CANCELLED` status (unlike Proforma Invoice), so "active" simply means anything short of `COMPLETED`. Attempting to generate a second one while an active JEO exists returns `409 Conflict`. Enforced at the application/service layer (a `findFirst` check before create), not a database-level unique index, for the same schema-drift-avoidance reason as Proforma Invoice's duplicate check.
- `jeoNumber` is auto-generated in the format `JEO-<year>-<6-digit-sequence>` (e.g. `JEO-2026-000001`), year-scoped with a retry-on-conflict loop — the same pattern as `ProformaInvoice.invoiceNumber`, `SalesOrder.salesOrderNumber`, `Quotation.quotationNumber`, and `Lead.leadNumber`.
- A `ProductionChecklist` row (all seven booleans `false`, no `completedAt`) is created in the same request as its `JobExecutionOrder`, and never created standalone. Its `jeoId` is a unique foreign key, so it's always exactly one checklist per JEO.
- Every new JEO starts as `PENDING`. Status only moves through `MATERIAL_READY` → `ASSEMBLY_STARTED` → `QC` → `READY_FOR_DISPATCH` → `COMPLETED` via the dedicated `PATCH /api/v1/job-execution-orders/:id/status` endpoint (or the "Change Status" dialog) — never as a side effect of a checklist update. Setting status to `COMPLETED` also stamps the checklist's `completedAt` — this is done explicitly by the service when a status change is requested, not auto-inferred from the checklist booleans, so a supervisor always makes the final call rather than the last checkbox silently finishing the job.
- The three named quick-action buttons (Start Production, Mark QC Complete, Ready For Dispatch) are convenience shortcuts layered on the status/checklist endpoints: each is visible only at the specific status it moves forward from (`PENDING`/`MATERIAL_READY`, `ASSEMBLY_STARTED`, and `QC` respectively), and each flips the checklist boxes that step implies (e.g. Start Production checks Material Issued + Assembly Started) together with the status change. This mapping was not spelled out field-by-field in scope, so it's a deliberate, documented interpretation — reaching `COMPLETED` is intentionally left to the generic Change Status dialog, since it isn't one of the three named buttons.
- Priority uses its own `JeoPriority` enum (`LOW` / `MEDIUM` / `HIGH` / `URGENT`), scoped to this model rather than reusing `Lead.priority`'s enum — the same "don't cross-wire modules" convention used for every other per-model status enum in this schema, so a future change to Lead's priority scale never silently changes JEO's.
- There is no edit and no delete for this module (no `deletedAt` column exists on `JobExecutionOrder`, per the given field list).
- The Production Dashboard's "active JEOs" table uses the same definition of "active" as duplicate prevention above (anything short of `COMPLETED`); the six summary cards above it count **all** JEOs regardless of active/completed, since a "Completed" card wouldn't make sense otherwise.
- The Timeline (`GET /api/v1/job-execution-orders/:id/timeline`) is built entirely from records that already exist elsewhere in the schema — no new tracking table or timestamp columns were added for it ("use existing JEO records"), which means two of its ten steps are necessarily best-effort rather than exact:
  - **Lead Created** — there is no foreign key from `Quotation` back to the `Lead` that produced its `Customer` (a Customer can exist from direct entry or from converting any number of unrelated Leads). The timeline finds the earliest `Lead` with `customerId` equal to this JEO's customer and treats that as "the" originating lead; if none exists (the customer wasn't created via lead conversion), this step is simply shown as not reached rather than guessed at.
  - **Production Started / QC / Dispatch** — `JobExecutionOrder.status` is a single mutable column, not a history log, so there's no stored timestamp for exactly when an earlier transition happened. These three steps are marked done/not-done from the JEO's *current* status and Production Checklist flags, and only get a timestamp when they equal the JEO's current status (using `updatedAt` as an approximation) — earlier steps that have already been passed show as done with no timestamp. "Dispatch" maps to the `READY_FOR_DISPATCH` status, since `JeoStatus` has no separate `DISPATCHED` value the way `SalesOrderStatus` does.
  - The other seven steps (Customer Created, Quotation Created, Sales Order Created, Proforma Invoice Generated, JEO Generated, and Completed) all use a real stored `createdAt`/`completedAt` timestamp.

## Business Rules (Sales Automation)

Full write-up in `SALES_AUTOMATION_CHECKLIST.md`. Summary of the rules that govern this
extension of the Quotation/Sales Order/Proforma Invoice/JEO chain above:

- **Price Validation** — `Product.minPrice` is a hard floor. Accepting a Quotation
  (`PATCH /api/v1/quotations/:id/status` with `status: "ACCEPTED"`) is blocked with a `400`
  (`code: "PRICE_BELOW_MINIMUM"`, with the offending items' entered/minimum/difference) if any
  item's `unitPrice` is below its product's `minPrice`. Administrators bypass this check
  entirely, the same "Administrator always wins" convention already used for permissions.
- **Approval Matrix** — a reusable, configurable engine (`ApprovalMatrix` table: module,
  min%/max% bracket, required Role) rather than a hardcoded threshold. `QuotationsService`
  computes the highest per-item discount % against each item's product `standardPrice` and
  looks up the bracket for the `Quotation` module; if the current user doesn't hold the
  required role (and isn't Administrator), acceptance is blocked with `400`
  (`code: "APPROVAL_REQUIRED"`, with the computed discount % and required role name). The same
  `resolveRequiredRole(module, percent)` method is written to be reused by any future module
  without new code — only new seed rows.
- **Approval Requests** — the only way past either block besides fixing the price. Submitting
  one (`POST /api/v1/quotations/:id/request-approval`) snapshots the discount %/below-minimum
  flag at request time. Deciding it (`PATCH /api/v1/quotations/approval-requests/:requestId/decide`,
  or the Quotation Approvals page) as the required role or Administrator performs the full
  ACCEPTED transition directly on approval — the requester never has to separately click Accept
  again. Only one `PENDING` request may exist per quotation at a time (`409` otherwise).
- **Send Quotation** — `POST /api/v1/quotations/:id/send` renders a PDF (`PdfService`), sends it
  as an email attachment (`MailerService`, template key `QUOTATION`), records an `EmailHistory`
  row, and sets `status="SENT"` plus `sentAt`/`sentBy`/`sentToEmail` — all as one atomic
  operation. It's available from Quotation Details whenever status is `DRAFT` or `READY`.
- **Email Templates & Mailer** — `EmailTemplate` rows (Quotation, Order Confirmation, Proforma
  Invoice, JEO Notification, Dispatch) are matched by a fixed `key` and support `{{token}}`
  substitution. `MailerService` builds a real SMTP transport from `SMTP_HOST/PORT/USER/PASS/SECURE/FROM`
  env vars when set; if `SMTP_HOST` is unset, it logs a `"SIMULATED"` send instead of throwing —
  mirroring this codebase's existing "Future Ready placeholder" convention rather than
  introducing a new one. Every send, real or simulated, writes an `EmailHistory` row and never
  throws back into the caller (a failed/simulated email never blocks the business transaction
  that triggered it).
- **Cascade automation** — accepting a Quotation (directly or via an approved request) converts
  the Lead to a Customer if not already one, creates the Sales Order, then the Proforma Invoice
  (customer + `FINANCE_TEAM_EMAIL` CC), then the JEO (factory notification to
  `FACTORY_NOTIFICATION_EMAIL`) — each step reuses that module's own `create()`/`createFromX()`
  method (see `SalesOrdersService.createFromQuotation()`, `ProformaInvoicesService.createFromSalesOrder()`,
  `JobExecutionOrdersService.createFromSalesOrder()`), so manual creation via each module's
  existing UI button and this automatic path share identical behavior — including the existing
  duplicate-prevention guards, which make every step in the cascade idempotent.
- **Audit Log** — a generic, append-only log (`AuditLog`: module, `recordId` as a plain string,
  action, actor, old/new value, remarks) records every Create/Update/Delete/Assign/Send
  Email/Generate JEO/Generate PI action across Quotation, Sales Order, Proforma Invoice, and JEO.
  `recordId` is the one deliberate exception to "use foreign keys, not denormalization" in this
  schema — a generic log needs to reference arbitrary entity types, which a real FK can't do.
  `EmailHistory`, by contrast, only ever needs one of a small fixed set of document types, so it
  does use real (nullable) foreign keys.
- **Lead history additions** — `QUOTATION_SENT`, `SALES_ORDER_CREATED`,
  `PROFORMA_INVOICE_GENERATED`, and `JEO_GENERATED` are synthesized into `getHistory()`'s
  response the same way the pre-existing `QUOTATION_CREATED`/`CUSTOMER_CONVERTED` entries are —
  never persisted directly, always derived from the linked Quotation/Sales Order/Proforma
  Invoice/JEO records at read time. Assignment History and Status History had storage tables
  from an earlier session but no read endpoint until now; both are exposed as their own tabs on
  Lead Details alongside the existing History/Notes tabs, plus a new Email History tab.

## Business Rules (Materials)

- `MaterialCategory` and `MaterialUnit` are real, FK-enforced lookup tables — deliberately separate from `Product.category`, which is free text. The Material Master spec calls for "Required Category"/"Required Unit" as validations against an actual foreign key, not just a non-empty string, so `Material.categoryId`/`Material.unitId` are enforced relations; creating or updating a Material with a `categoryId`/`unitId` that doesn't exist returns `400 Bad Request`.
- `materialCode` is unique and user-supplied (not auto-generated, unlike `leadNumber`/`quotationNumber`/etc.) — creating or updating a Material with a code that already belongs to a different row returns `409 Conflict`.
- `currentStock`, `minimumStock`, `maximumStock`, and `reorderLevel` are all validated as non-negative on both create and update (`400 Bad Request` if violated) — this is the "Current Stock cannot be negative" rule from scope, applied consistently to the other stock fields too since a negative minimum/maximum/reorder level would be equally meaningless.
- `supplierId` and `warehouseId` are plain optional string scalars, not real relations — no Supplier or Warehouse module exists yet in this schema, the same convention already used for `Lead.assignedTo`/`SalesOrder.createdBy`/`JobExecutionOrder.assignedTo`. A future Supplier/Warehouse module could turn these into real relations without renaming either column.
- Deactivating a material is a soft delete (`isActive=false`), same convention as Customer/Product (not the `deletedAt` convention used by Lead/Quotation/SalesOrder) — the Material Master field list includes `isActive`, not `deletedAt`.
- Stock status (`In Stock` / `Low Stock` / `Out of Stock`) is derived, never stored: `currentStock <= 0` is Out of Stock, `0 < currentStock <= reorderLevel` is Low Stock, anything above that is In Stock. The frontend computes this the same way client-side (`getMaterialStockLevel()` in `types/index.ts`) as the backend does for the Dashboard's Low Stock/Out Of Stock counts, so the badge shown in the Material List/Details always agrees with the Dashboard cards.
- `MaterialCategory`/`MaterialUnit` only have `GET` (list) and `POST` (create) endpoints — no `PATCH`/`DELETE`, and no dedicated management page. They exist solely to populate the Category/Unit dropdowns on the Material Form (which also has an inline "+" to create a new one without leaving the form) and to satisfy the Required Category/Required Unit validations.
- Excel import resolves Category and Unit **by name**, not id — a spreadsheet user works with "Mild Steel" and "Kg", not UUIDs. Names are matched case-insensitively; a row whose category or unit name doesn't already exist fails that row (with a descriptive error) rather than silently creating a new lookup row, so imports can't accidentally spawn duplicate/misspelled categories. Import upserts by `materialCode`: an existing code updates that material, a new code creates one. Each row is processed independently inside its own try/catch, so one bad row (bad category name, negative stock, missing code) doesn't abort the rest of the file — the response reports exactly which rows succeeded, which were created vs. updated, and why any row failed.
- Excel export produces the same column layout the import expects (`materialCode, name, description, category, unit, supplierId, cost, minimumStock, maximumStock, reorderLevel, currentStock, warehouseId, isActive`), so an exported file can be edited and re-imported directly.

## Business Rules (Suppliers)

- `supplierCode` is auto-generated (e.g. `SUP-000001`), never accepted from the client, with the same retry-on-conflict-and-regenerate loop used for `Lead.leadNumber`/`Quotation.quotationNumber`/etc. — the client never types or edits it, including on the Edit form, where it's shown read-only.
- **Only Supplier Name is required.** GST Number, PAN Number, Contact Person, Phone, Email, Website, Address, City, State, Country, PIN Code, Payment Terms, Lead Time, Currency, and Remarks are all optional, on both the manual Create/Edit form and Excel import — a blank value is accepted and simply left blank, never an error. If Email, Phone, or Lead Time *is* provided, it's still format-checked (a valid email address; 10–15 digits after normalization for phone, see below; a non-negative number for lead time) — presence is optional, but garbage data in a filled field is still flagged.
- Phone normalization (manual entry and Excel import both go through this): a leading apostrophe (the text-format marker some CSV/XLSX exports add to numeric-looking cells) is stripped, and a leading `+` country code is preserved rather than being stripped along with the rest of the punctuation — e.g. `'+91 93122 45259` normalizes to `+919312245259`. This is the same normalization approach used for Lead Import's phone field.
- `status` defaults to `ACTIVE` when omitted (manual create and import both). Deleting a supplier (`DELETE /api/v1/suppliers/:id`) is a separate, independent soft delete (`deletedAt` timestamp, same convention as Lead/Quotation/SalesOrder) — a supplier's `status` and whether it's been deleted are two independent concerns, the same way a Lead's `status` and `deletedAt` are.
- Supplier Import duplicate prevention: an exact, case-insensitive match on `supplierName` against a non-deleted supplier is treated as a duplicate (Supplier Name is the only required/identifying field, so it's the only thing to match on — the same "match on what's actually required" convention as Lead Import's companyName+email check). This also catches duplicates **within the same uploaded file**, the same way Lead Import does: rows are processed one at a time in order, and each row's duplicate check queries the database fresh, so an earlier row in the same file that was just inserted is visible to a later row's check.
- The Preview step (`POST /api/v1/suppliers/import/preview`) runs every row through this exact same validation and duplicate-detection logic but never inserts anything. The commit step (`POST /api/v1/suppliers/import`) re-runs the identical logic on whatever rows it's sent (normally just the ones Preview classified as `valid`) rather than trusting the client's earlier classification — the same defensive pattern Lead Import and Material Import both use.
- Extra columns in the uploaded file are ignored, and any of the 16 non-required columns can be missing from the file entirely — columns are matched by header name (case-insensitive, with a couple of common synonyms like "GSTIN" for GST Number and "PIN Code"/"Pincode"/"Zip Code"), not position.
- The final import summary reports three counts: **Imported** (rows actually inserted), **Duplicates** (skipped — matched an existing supplier or an earlier row in the same file), and **Failed** (skipped — missing Supplier Name, or a provided Email/Phone/Lead Time/Status that didn't pass validation), plus the full per-row detail behind each count — same wording as Lead Import's summary.
- The Dashboard's Suppliers count is a live `count()` of non-soft-deleted suppliers, so newly created/imported suppliers are reflected the moment the Dashboard is next viewed/refocused.
- `Material.supplierId` (added by the Material Master module) remains an unrelated plain string scalar, not a foreign key to this new `Supplier` table — turning it into a real relation was out of scope for this module and would be a separate, deliberate follow-up, not a silent side effect of adding Supplier Master.

## Business Rules (Enterprise RBAC)

- A User can hold multiple Roles (`UserRole` join table); a Role can hold multiple Permissions (`RolePermission` join table). A user's effective permission set is always the **union** of every Permission granted by every Role they currently hold — there's no concept of a "primary" role or of one role's permissions overriding another's.
- Every Permission is a `(module, action)` pair (e.g. `(Lead, View)`, `(Quotation, Approve)`), stored with its own `module`/`action` columns plus a derived, unique, lowercased `code` column (`"lead.view"`, `"quotation.approve"`) — both the backend guard and the frontend `hasPermission(module, action)` helper match on this `code`, never on the role name or the legacy `User.role` string.
- **APIs are protected by permission, never by role name.** Every existing controller (Leads, Customers, Products, Quotations, Sales Orders, Proforma Invoices, Job Execution Orders, Materials, Material Categories, Material Units, Suppliers) plus the four new RBAC controllers now carries `@UseGuards(JwtAuthGuard, PermissionsGuard)` at the class level and a `@RequirePermission(module, action)` decorator on each handler; `PermissionsGuard` reads that handler's required permission code and checks it against `request.user.permissions` (computed by `JwtStrategy` — see below), throwing `403 Forbidden` if it's missing. Nowhere in guard or service code is there a check like `if (user.role === 'admin')` — the spec's own worked example, `quotation.approve`, is enforced exactly this way on `PATCH /api/v1/quotations/:id/status`.
- **Administrator gets every permission through RolePermission, not a code bypass.** The seed script assigns every single Permission row to the Administrator role via `RolePermission` at seed time (`ROLE_PERMISSIONS.Administrator = <all permissions>`). If a new Permission is added later and Administrator should have it, that's a data change (seed it, or assign it via the Roles screen) — not a code change, since no code path special-cases "Administrator" or "admin" at all.
- Permissions are always resolved **fresh, per request** — `JwtStrategy.validate()` calls `UsersService.findByIdWithAccess()` on every authenticated call, which re-queries the user's current roles → role permissions from the database (nothing is cached in the JWT payload itself, which only ever contained `{ sub, email, role }`). This means changing a user's roles, or a role's permissions, from the admin screens takes effect on that user's *very next request* — no re-login required, and no token refresh needed.
- A disabled user (`isActive = false`, via the Users screen's Disable action or `DELETE /api/v1/users/:id`, which is the same thing) is rejected the same way: `JwtStrategy.validate()` returns `null` if `!user.isActive`, so their existing JWT stops working on their next request even if it hasn't expired yet.
- `PermissionsGuard` is deliberately **not** registered as a global (`APP_GUARD`) guard. NestJS always runs global guards before controller/method-scoped ones, which would run the permission check before `JwtAuthGuard` populates `request.user` — breaking every check (it would always see `request.user` as `undefined`). Instead, every controller composes both guards explicitly, in order, via `@UseGuards(JwtAuthGuard, PermissionsGuard)`.
- Menus are permission-driven, not role-driven, on the frontend too: `Sidebar.tsx` has no `if (user.role === ...)` anywhere. Every nav item declares the `{ module, action }` it needs (or none, for universally-visible items), and `hasPermission()` — backed by the same `user.permissions` codes the backend computed — decides what's shown, down to hiding an entire collapsible group when none of its items qualify.
- Deleting a Role cascades to its `RolePermission` rows and to any `UserRole` rows referencing it (`onDelete: Cascade` on both), so a user who only held that role loses it outright, not gets left with a dangling reference. Deleting a Department only detaches it from its Users (`onDelete: SetNull` on `User.departmentId`) — deleting a department never deletes or deactivates the people in it.
- Editing a Role's permissions or a User's roles both use the same "replace the entire list" pattern already established elsewhere in this codebase (Lead's products, Quotation's items): the join table's existing rows for that parent are deleted, then recreated from whatever array was submitted, inside a single transaction — never a diff/add/remove.
- The pre-existing `User.role` free-text column (e.g. `"admin"`) is left completely alone — same values as before RBAC, same places it's read (`AuthService`, `JwtStrategy`'s legacy field) — since real authorization now flows entirely through `roles`/`permissions` instead. It exists for display/legacy-compatibility only and is never consulted by any guard.
- **Exactly one user is hardcoded: the seeded System Administrator.** `prisma/seed.ts`'s `DEFAULT_USERS` array has a single entry (name, username `admin`, email `admin@smartrotamac.com`, password `Admin@123`, Role Administrator, Department none, Active, `mustChangePassword: true`). Every other user — Sales Manager, Sales Executive, Production, Finance, Stores, or anyone else — must be created dynamically from **Administration → Users**; there is no code path that seeds or auto-creates additional users. (The six *Roles* of the same names are still seeded as a catalog, per the original Enterprise RBAC spec — that's a Role existing and being assignable, not a User.)
- **Login accepts either Username or Email** in a single field (`identifier` in `LoginDto`). `UsersService.findByUsernameOrEmail()` does one `findFirst` with `OR: [{ email }, { username }]`, both compared lowercased. `username` is its own unique, required column (3-32 characters: letters, numbers, dot, underscore), set at creation and editable via general Edit (uniqueness re-checked on change) — separate from `email`, which remains its own unique column exactly as before.
- **Force Password Change on First Login.** Every user — the seeded Administrator, and every user created via Administration → Users — starts with `mustChangePassword = true`. `ProtectedRoute` on the frontend checks this on every route change and redirects to `/change-password` for as long as it's true, regardless of what URL was requested; there is no way to reach any other screen until it clears. It's cleared **only** by `POST /auth/change-password` (self-service: requires knowing the current password) succeeding — an Administrator resetting someone else's password (see next bullet) sets it back to `true`, it never gets cleared any other way.
- **Reset Password vs. Edit User are two distinct actions**, matching the spec's own separate bullets. General Edit (`PATCH /api/v1/users/:id`) no longer accepts a password field at all — `UpdateUserDto` explicitly omits it. Reset Password is its own endpoint (`POST /api/v1/users/:id/reset-password`, `User.Edit` permission, same as Edit) that sets a new password without needing the old one and always sets `mustChangePassword = true`, since a password an Administrator just typed in on someone else's behalf is inherently temporary.

## Notes

- Database models: `User` (auth), `Department`, `Role`, `Permission`, `RolePermission`, `UserRole`, `Customer`, `Product`, `Lead`, `LeadProduct`, `Quotation`, `QuotationItem`, `SalesOrder`, `SalesOrderItem`, `ProformaInvoice`, `JobExecutionOrder`, `ProductionChecklist`, `MaterialCategory`, `MaterialUnit`, `Material`, and `Supplier`.
- Customer validation: Company Name and Contact Person are required; Phone is required and must be 10–15 digits; Email is optional but must be valid if provided; GST Number is optional.
- Product validation: Name and Category are required; SKU, Description, and Price are optional; Price must be a positive number if provided.
- Lead validation: Company Name, Contact Person, Phone, and Title are required; Phone/Alternate Phone must be 10–15 digits if provided; Email must be valid if provided; Estimated Value must be a positive number if provided; each product line requires a product and a quantity of at least 1; Industry is optional free text. Lead Import validation (Company Name, Contact Person, Email, and Phone required per row; Title auto-defaulted; unrecognized Lead Source/Status values flagged rather than defaulted) is documented separately in Business Rules (Lead Import) above, since it's stricter than manual creation in a couple of ways (e.g. Email is required for import but optional when creating a lead by hand).
- Quotation validation: Customer is required; at least one item is required; each item requires a product and a quantity of at least 1; unit price and GST percent must be positive numbers if provided.
- Sales Order validation: Quotation is required (and must be Accepted); at least one item is required; each item's product must belong to the quotation and have a quantity of at least 1; advance percentage must be between 0 and 100; unit price, discount, and GST percent must be positive numbers if provided.
- Proforma Invoice validation: Sales Order is required and must exist (`customerId`, items, and amounts are never accepted from the client — always copied server-side); `invoiceDate`/`validUntil` must be valid dates if provided; all other fields (payment terms, bank name, account number, IFSC code, branch, notes) are optional free text.
- Job Execution Order validation: Sales Order is required and must exist (`customerId`, `quotationId`, `deliveryDate`, and products are never accepted from the client — always copied server-side); `priority` must be one of `LOW`/`MEDIUM`/`HIGH`/`URGENT` if provided (defaults to `MEDIUM`); `assignedTo` and `remarks` are optional free text. Production Checklist fields are always booleans, PATCHed independently.
- Material validation: Material Code and Name are required; Category and Unit are required and must reference an existing `MaterialCategory`/`MaterialUnit` row; Current Stock, Minimum Stock, Maximum Stock, and Reorder Level must all be non-negative numbers if provided (Current Stock defaults to 0 if omitted); Material Code must be unique; Cost must be non-negative if provided; Supplier, Warehouse, and Description are optional free text.
- Supplier validation: Supplier Name is the only required field; Email must be valid if provided; Phone must be 10–15 digits (after normalization — see Business Rules (Suppliers) above) if provided; Lead Time must be a non-negative number if provided; GST Number, PAN Number, Contact Person, Website, Address, City, State, Country, PIN Code, Payment Terms, Currency, Remarks, and Status are all optional (Status defaults to `ACTIVE`); Supplier Code is always auto-generated and never user-editable.
- Deactivating a customer/product/material, or deleting a lead/quotation/sales order/supplier, is a soft delete (`isActive=false` for Customer/Product/Material, `deletedAt` timestamp for Lead/Quotation/SalesOrder/Supplier) — the record stays in the database and just drops out of the active list/catalog/pipeline. `ProformaInvoice` and `JobExecutionOrder` have neither column, per their given field lists — Proforma Invoice's "no longer active" equivalent is `status = CANCELLED`; JEO has no such escape hatch at all (any status short of `COMPLETED` counts as active) — and neither has any delete capability.
